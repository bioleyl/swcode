# TICKET 5 — Refactor commands (refactor / explain / fix problems / add tests)

**Goal.** The developer can act on the code with one command from the palette or the editor's context menu — *Refactor*, *Explain*, *Fix problems*, *Add tests* — and the command sends a preset prompt to swcode carrying the selection and, when it helps, the file's diagnostics. Today only one generic `swcode.ask` exists, so every refactor needs the person to type the whole request.

**Scope.**
- **Manifest (`vscode/package.json`):** contribute the four commands next to `swcode.ask`, in the palette and in `editor/context` (a `swcode@2..@5` group after `swcode.ask`):
  - `swcode.refactor` — title "swcode: Refactor"
  - `swcode.explain` — title "swcode: Explain"
  - `swcode.fixProblems` — title "swcode: Fix problems"
  - `swcode.addTests` — title "swcode: Add tests"
  Keep `swcode.ask` as it is.
- **Extension (`vscode/src/extension.ts` + `swcode.constants.ts`):** register the four commands; each calls the panel with its own prompt text. Put the prompt texts in `swcode.constants.ts` as named constants (next to `ASK_PROMPT`) — short, plain, language-agnostic, e.g. "Refactor the selected code, keeping its behaviour." / "Explain what this code does." / "Fix the problems reported for this file." / "Add tests for the selected code." The command handler reuses ticket 3's `ask(webview, text)` (`vscode/src/context.ts`) and shows the panel, exactly like `swcode.ask`.
- **Channel (the one extension to ticket 3's message):** the host→bundle prompt message carries a flag for the diagnostics, `{kind:'prompt', text, includeProblems?}` — `hostMessageFrom` in `web/src/services/host-messages.ts` parses it (absent → the composer's current default) and `hostMessageBus` delivers it, so `ScComposer`'s existing `hostContext` + `includeProblems` state (ticket 3) shows the selection *with* the problems when the command asks for them. `SessionPanel.ask` (and `context.ts`'s `ask`) take the flag; the webview page's forwarding script needs no change (it forwards `event.data` whole).
- **Per-command default:** *Fix problems* asks with the problems included; *Refactor*, *Explain* and *Add tests* send the selection and leave the "Include problems" toggle to the person (their default is the composer's). No new UI beyond the manifest entries — the composer's existing toggle is the affordance.
- **No new daemon calls and no new dependencies**: the four prompts go over the existing socket messages; the selection/diagnostics come from ticket 3's context.

**Acceptance criteria.**
- `npm run build`, `npm run build:vscode`, `npm run typecheck` (web, e2e, vscode), `npm run lint` and `npm run check` stay green.
- Vitest coverage for the new seams, in the existing test files' style:
  - `vscode/tests` (fake `vscode` module): the four commands are registered and each posts its own prompt text + its `includeProblems` flag to the webview; the palette and `editor/context` contributions exist in `package.json` (read the manifest in a test, as the scaffold's test does).
  - `web/tests/host-messages.test.ts`: `hostMessageFrom` reads `includeProblems` (true, false, absent) and keeps parsing the ticket-3 shape without it.
- Headless-browser check of ticket 1's/2's/4's recipe (AGENTS.md: built daemon + `serve` with a scratch `SWCODE_DATA_DIR`, generated webview page, `http-server`, screenshot): a `postMessage` of `{kind:'prompt', text, includeProblems:true}` lands in the composer as the text with the problems block attached (the `.problems` button reads "Problems included"); a prompt without the flag lands with the selection only.
- The web app's entry is unchanged in behaviour: the composer behaves as today when no host gives a context.
- Report the exact message shape with the new flag, the files changed in `web/` and `vscode/`, and the four prompt texts verbatim — ticket 6 (packaging and docs) documents them.

**Notes for Dev.** Follow the swcode-base rules (read before editing, business rules in services, small functions, named constants, types in `types/`). Keep the shared components shared: the composer gains nothing new, it only receives the flag. The e2e suite runs the built bundle, so a web change needs `npm run build` before `npx vitest run --config vitest.e2e.config.ts`.
