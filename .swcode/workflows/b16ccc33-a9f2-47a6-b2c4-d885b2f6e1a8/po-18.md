# TICKET 6 — Packaging and docs (the last ticket)

**Goal.** Ship the extension as a real, installable `.vsix` that carries everything tickets 1–5 added, and document it in the repo's README so a user knows what it is, how to install it, and what its commands do. This closes the brief: the second UI is built, packaged, and explained.

**Scope.**
- **Repackage the `.vsix`.** The `dist/swcode-0.1.0.vsix` on disk is ticket 2's; regenerate it with the existing `npm run package:vscode` (which runs `build:vscode` — the shared bundle + esbuild — then `vsce package --out ../dist/`) so the artifact carries ticket 3's context, ticket 4's Open affordance, and ticket 5's four commands. Confirm the produced `.vsix` contains `out/extension.js` with all five commands and the Open affordance (inspect with `unzip -l dist/swcode-*.vsix` and grep the bundled `extension.js` for `swcode.refactor`/`swcode.explain`/`swcode.fixProblems`/`swcode.addTests`/`open`). The bundle is served by the daemon, so the `.vsix` ships no web assets (ticket 1's note) — keep `.vscodeignore` as is (it excludes `src`, `tests`, `tsconfig.json`, `*.map`, `*.ts`). Keep the version at `0.1.0`; the repackaged file replaces the stale one. No new build tooling.
- **README section.** Add a "VS Code extension" section to `README.md` (place it with the other UI surfaces, near "Windows desktop app"). Cover, in the README's voice (terse, one idea per bullet):
  - What it is: a second, smaller UI for the daemon on this machine — the session panel in the side bar, reusing the web app's components; the feature subset (session list, conversation, composer, stop, answer a question/permission).
  - Install: build the `.vsix` with `npm run package:vscode` (needs the daemon's web bundle), install it in VS Code (Install from VSIX).
  - Daemon discovery: reads the port from `~/.swcode/settings.env` (`SWCODE_PORT`, default 4500) and the token from `~/.swcode/token` (`SWCODE_DATA_DIR` wins over `~/.swcode`); the status bar shows whether the daemon is reachable (probed at activation and every 15s); the panel works when the daemon is down (its own status alert).
  - The five commands and their prompt texts, verbatim: **Ask swcode** (empty), **Refactor** ("Refactor the selected code, keeping its behaviour."), **Explain** ("Explain what this code does."), **Fix problems** ("Fix the problems reported for this file."), **Add tests** ("Add tests for the selected code.") — palette + editor context menu.
  - The "Include problems" toggle (the `.problems` affordance in the composer; its label reads "Include problems" / "Problems included"): a prompt that carries no `includeProblems` flag uses the composer's toggle, and the composer that shows a sent prompt is the session page's fresh instance (its toggle is at the default) — say this so the reader isn't surprised. *Fix problems* sends with the problems included; the other three leave the toggle to the person.
  - Open: clicking a file in a tool row / diff opens it in the editor at the right line (the editor follows the agent's edits).
  - Theming: light/dark follows VS Code's active colour theme, mapped onto the `--jl-*` tokens.
- **Tests for the shared UI entry.** Confirm the entry's host-config parsing is covered (`web/tests/host.test.ts` covers `?daemon`/`?token`/`?theme`); add coverage only for a seam the later tickets introduced that is not yet tested (e.g. the bundle's `--vscode-*` theme override reaching the frame, if a cheap unit test fits). Do not rewrite existing tests.
