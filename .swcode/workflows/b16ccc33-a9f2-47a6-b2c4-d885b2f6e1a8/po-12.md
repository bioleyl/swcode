# PO — tickets 1–3 accepted, handing off ticket 4

**Brief, in my words.** A VS Code extension that is a *second, smaller UI* for the swcode daemon already running on the same machine: the developer gets swcode's agent inside the IDE (session list, conversation, composer) and the agent gets the IDE's intelligence (language-server diagnostics, active file + selection, refactor prompts). The UI reuses the web app's `sc-*` components through one shared bundle so nothing is drawn twice, and the feature set stays deliberately smaller than the web app's.

**Backlog (ordered).**
1. Shared UI bundle entry — **accepted** (po-1 → dev-2 → qa-3).
2. Extension scaffold + live session panel — **accepted** (po-4 → dev-5 → qa-6).
3. IDE context in the prompt — **accepted** (po-7 → dev-8 → qa-9 → qa-11).
4. **IDE feedback** — *this ticket, full text below*.
5. Refactor commands (refactor / explain / fix problem / add tests as preset prompts).
6. Packaging and docs (`.vsix` wired into the repo's scripts, README section, shared-UI-entry tests).

po-1's assumptions still stand (side-bar webview, on-demand diagnostics, prompt-style refactorings, no daemon autostart, `vscode/` folder, `--jl-*` theming, no new daemon API). qa-11's notes are folded in: "Ask swcode" with no file open sending an empty prompt is accepted as-is, and a smoke pass in a real VS Code is welcome but does not block ticket 4.

**Decision for this ticket** (recorded): a click opens the file at the changed range (`showTextDocument` + `Range`), not VS Code's diff editor — the diff display already carries the path and the line numbers, and a real diff editor would need the pre-edit content the socket does not keep.

# TICKET 4 — IDE feedback (open a file/diff in the editor, follow the agent's edits)

**Goal.** The conversation stops being a read-only log: clicking a file in a tool row (or a line of its diff) opens it in VS Code at the right place, and the editor keeps up with the agent's edits. The developer reads what the agent changed in the real editor, not in a copy.

**Scope.**
- **Bundle side (web/, ticket 1's entry — reuse, do not fork):**
  - The outbound half of the host channel: `web/src/services/host-messages.ts` gains a `requestOpenInHost(path, startLine?, endLine?)` (a `window.parent.postMessage({type:'open', …})`, a no-op when there is no host). Keep `hostMessageFrom`/`hostMessageBus` as they are; this is the reverse direction of ticket 3's channel.
  - `sc-tool-row`: when the call concerns a file (the `diff` display's `path`, and the file tools whose summary names a path), give the row an "Open" affordance (a `jl-icon`/`jl-button` in the head, next to the chevron) that asks the host to open it. `sc-diff` gets one host affordance too: clicking a line opens the file at that line (`DiffLine.newLine`, falling back to `oldLine`). One new prop/affordance per component, no parallel component; the app's entry keeps working (the affordance is harmless in a plain browser, where `window.parent === window`).
  - Path resolution stays in a service (e.g. `web/src/lib/ide-open.ts` or beside `host-messages.ts`): a tool's path is relative to the project, so resolve it against the session's project path (`session.projectId` → the `projects` the socket pushes at connect, `services/project-list.ts`), and send the host an absolute path. Keep the pure function covered by a vitest test.
- **Webview page side (`vscode/src/lib/webview-html.ts`):** the inline `FORWARD_SCRIPT` becomes two-way — a `window.addEventListener('message')` that forwards a message tagged as coming from the bundle to `vscode.postMessage(data)` and everything else into the frame (keep the existing host→frame direction, keep the CSP as it is: inline script, `style-src 'unsafe-inline'`, nothing new).
- **Extension side (`vscode/`):** a `webview.onDidReceiveMessage` handler, registered in `SessionPanel.resolveWebviewView` and pushed into the extension's `subscriptions` (the pattern ticket 3's `startContext` uses). For `{type:'open'}`: `workspace.openTextDocument(uri)` then `window.showTextDocument(uri, { preview: true, selection: new Range(startLine-1, 0, endLine-1, 0) })` (1-based lines → 0-based `Range`; a missing line range opens the file whole). A path that cannot be opened shows the status bar's message and does not crash.
- **Following the edits:** VS Code refreshes an open document when the daemon writes the file (its file watcher) — nothing to implement beyond opening; confirm it and note it. Do not re-open the file on every `toolFinished` (no tab churn); the click drives it.
- **No new daemon calls**: the path and the line numbers come from the existing `toolFinished.display` (`{kind:'diff', path, lines[]}`).

**Acceptance criteria.**
- `npm run build` and `npm run build:vscode` succeed; `npm run check` stays green (biome, `tsc -p web|e2e|vscode`, vitest, go). Add vitest coverage for the new seams: the open request's shape + path resolution (web), the webview page's two-way forwarding script (`vscode/tests/webview-html.test.ts`), and the extension's message → `Range` mapping (`vscode/tests`, with a fake `vscode` module as the existing tests do).
- In the headless-browser check of ticket 1's/2's recipe (AGENTS.md: built daemon + `serve` with a scratch `SWCODE_DATA_DIR`, generated webview page, `http-server`, screenshot): opening a session with a diff row shows the "Open" affordance, and a click posts the `{type:'open'}` message (assert it with a probe page that records `window.onmessage`, or the extension's unit test).
- The web app's entry is unchanged in behaviour: the tool rows and diffs render as today, the "Open" affordance posts to its own window and nothing breaks.
- The app's bundle and the extension's entry stay in step (the shared `sc-app-shell` chunk carries the same row markup for both entries).
- Report the exact message shape (bundle → webview page → extension), the files added/changed in `web/` and `vscode/`, and what the editor shows for a diff (the file at the changed range) — ticket 5 (refactor commands) builds on the same channel.

**Notes for Dev.** Follow the swcode-base rules (read before editing, business rules in services, small functions, types in `types/`). Keep the shared components shared: one affordance on `sc-tool-row`, one on `sc-diff`. The e2e suite runs the built bundle, so a web change needs `npm run build` before `npx vitest run --config vitest.e2e.config.ts`.
