# swcode: notes for working on the code

Read `README.md` first.

## Conventions

- The daemon is Go (`cmd/swcode`, `daemon/`, `desktop/`), the app TypeScript (`web/`).
- The protocol lives in `shared/protocol/` as zod schemas: the app parses with them, and `npm run protocol` writes
  the daemon's Go types from them (`daemon/protocol/protocol_gen.go`, never edited by hand; `check:go` fails while
  it is stale). A new session event or socket message needs a handler on both sides: the app's handler maps
  (`SessionEventHandlers`, `ServerHandlers`) and the daemon's generated mappers (`ClientMessageMapper`…, through
  `MapClientMessage`) do not compile until it has one.
- The daemon's model of a session is its event list. Do not keep conversation state elsewhere: the model's
  messages (`daemon/agent/conversation.go`) and the app's drawing (`sc-conversation`) are both rebuilt from events.
- Keep the system prompt and the start of the conversation stable: anything that changes them (a date, a counter)
  makes llm-server process the whole prompt again at every step.
- Frontend: built from jlib's components (`@syware/jlib`), written by their class in JSX, as SyWare's UX lays them
  out: `JlAppShell` and `JlSideNav` for the frame, a `JlPage` for each page, `JlPageOutlet` showing them. swcode's
  own components keep atomic design (`atoms/`, `molecules/`, `organisms/`, `templates/`, `pages/`), extend
  `ScElement` (jlib's `JlElement`), their CSS in a `.css` file beside it imported with `?inline`. Colours, radii,
  spaces and fonts are jlib's `--jl-*` tokens only. The logo blue (`--jl-brand`) never carries small text: use
  `--jl-accent`. An icon a jl-* component draws by name is registered (`registerIcons`, lucide's; the usual ones in
  `lib/icons.ts`).
- A session's history is paged from its end: `openSession` takes an `events` limit and `sessionHistory` answers with `keptBack` (events older than those shown); `olderEvents` asks for the page above. The conversation view (`sc-conversation`) keeps the scroll rules in `lib/history-window.ts` and asks for more at its top; the page never learns the whole list until it is all pulled.
- **A turn's restore point is captured by wrapping its `hosts.Host`** (`daemon/checkpoints`, `Recorder.Host()` in `runTurnIn`): writes through tool hosts are copied before each first write. In a git repository on a host with a POSIX shell, what the turn's commands changed is kept too (`Recorder.WatchCommands`, `commands.go`): the workspace is written as a git tree when the turn starts and when it ends, with an index and objects of the session's own in its scratch folder (`<scratch>/git`, so the repository's index, objects and refs are never written), and the files that differ get their copies from the first tree. The turn's first `Run`/`StartJob` waits for the first look; files git ignores are kept only when a tool wrote them, links and nested repositories never; a change the person made by hand during the turn counts as the turn's. The service makes the turn id (`runningTurn.id`, `agent.Setup.TurnID`), and `agent.RunTurn` records `checkpointSaved` before `turnFinished` through `TurnHost.TakeCheckpoint`, so the turn still ends on its own event.
- A paired computer's colour lives in `computers.json` and reaches the page as `Computer.color`; `sc-computer-switch` puts it on `<html>` as `data-computer-color`, and `global.css` turns that into the `--jl-accent*`, `--jl-on-accent` and `--jl-focus-ring` tokens (the light and dark values use `light-dark()`).
- A project's page is four tabs at `/projects/:id/<tab>` (`sessions`, `todos`, `config`, `skills`; the list in `web/src/lib/project-tabs.ts`): the address's `tab` is a route attribute like settings' `topic`, a picked tab only rewrites it with `history.replaceState`, and `/projects/:id` alone shows the sessions tab. A new tab needs its label/icon in `PROJECT_TAB_LABELS`, a `JlTabPanel`, and the e2e tests open it before touching its card.
- A project's todos live on `protocol.Project.todos` in `projects.json`, changed with `addProjectTodo` / `setProjectTodoText` / `setProjectTodoDone` / `removeProjectTodo` (the daemon sends the whole `projects` list back); they are not a file of their own. A new session's `createSession.pinnedTodos` (texts, not ids) are appended by `sessions.withPinnedTodos` after the first user message, and its `pinnedTodoIds` make `Projects.LinkTodos` set their `sessionId`, which the Todo tab links back to the session and `sc-session-todos` lists in it.
- The e2e tests are one file per user-facing area (`e2e/session.e2e.test.ts`, `composer`, `projects`, `settings`, `navigation`, `layout`, `phone`, `mcp`); shared viewports, flows and page helpers (`start`, `settle`, `overflow`, `tab`, `navItem`…) live in `e2e/support.ts`, and every test file calls `afterEach(stopRigs)` or its rigs outlive the test.
- A terminal belongs to a project folder and host, not to a session: `daemon/terminals` keeps them (scrollback of 256 KiB each, titles numbered per folder as Terminal, Terminal 2…), the side panel of the session page lists the ones of the session's project, and the agent's `terminal` tool (`daemon/tools/terminaltools.go`) opens a titled one in the session's workspace. The session's host ref travels to tools in `tools.Context.HostRef`.
- Terminal output reaches only the sockets that attached (`attachTerminal`/`detachTerminal`, `terminals.Service.Watch`), as base64 because it is bytes; `terminalOpened.output` redraws a page that joins late, prefixed with a clear when the start of the scrollback was dropped. The page keeps xterm in `sc-terminal`, its colours read from `--jl-*` at open with a transparent background over the card, since xterm knows no CSS variables.
- A terminal is a `JlDialog size="full"` (`sc-terminal`): the side panel of the session page opens it, its own X leaves the view (the shell keeps running), its "Close terminal" action ends the shell. Its heading is the terminal's own name (read-only) and its description the state and folder; renaming is the side panel's (a pencil in the row turns the name into a field there), so the dialog keeps its header — an empty `JlDialog` heading leaves a blank strip, not a title. Escape is the terminal's key — xterm takes it, so it goes to the shell and never closes the dialog, and tests leave it through the dialog's "Close" button. One xterm serves every terminal of the page and clears itself when another terminal is shown, so each terminal keeps its own screen.
- The agent reads what a terminal printed with `readterminal { terminal?, lines? }` (`daemon/tools/terminaltools.go`): `terminal` takes a name or an id, and is left out for the workspace's only terminal — with several, the refusal lists their names. It resolves them from `terminals.Port.List()` filtered by the session's workspace and host, reads the end of the scrollback (100 lines, 500 at most, ANSI stripped at 12k characters) and is a read, so it needs no approval. It reads terminals the person opened too.
- Tool names stay one lowercase word (`websearch`, `readterminal`): biome's `useNamingConvention` refuses a snake_case key such as `terminal_output` in the app's label maps, and `pascal()` in `scripts/protocol-go.ts` would name the constant `ToolNameTerminalOutput` only with the underscore.
- A turn's restore point is shown as diffs: `checkpointDiff { sessionId, turnId }` answers only the asking socket with `checkpointDiff { files }` (`ToolDisplay` diffs), and `sc-conversation` opens `sc-checkpoint-diff` (a `JlDialog` of `sc-diff` per file) from the “Changes” button beside “Restore”. The daemon builds it in `sessions.Service.CheckpointDiff`: `checkpoints.Store.Snapshot` reads the pre-images, `currentText` reads each file as it is now, `tools.FileDiff` makes the hunks.
- The command line (`daemon/cli`) has one kind per action: `swcode` opens, `start`/`stop` run the daemon without a service, `serve` is the foreground daemon, `install` copies the program, `service install|uninstall` registers it, and `--update` (`update.Apply`) replaces the running binary. `daemon` is internal: it is the background process `StartInBackground` spawns, and `serve --service` is what a service manager runs. A service run exits 1 on a restart or update so the manager starts it again (systemd's `Restart=on-failure`, Windows' `RestartCount`); a clean stop keeps it stopped. Linux gets a systemd **user** unit (`~/.config/systemd/user/swcode.service`), Windows a logon Task Scheduler task that runs a hidden PowerShell; macOS is no longer built.
- The model opens and closes the project's todos with `todo` and `closetodo` (`daemon/tools/todostool.go`): the project is the session's workspace and host (`tools.Context.Todos`, implemented by `projects.Service.OpenTodo`/`CloseTodo`), the todo is matched by its whole text, and the pinned-todos message names both tools. They are the main agent's only (not a chat's or a subagent's), need no permission, and answer the project's whole list so the model sees what is left.
- A session's pins are `Meta.pins` (`[{ id, label }]`, the message's event id and its first line) and reach the app as `SessionSummary.pins`; `pinEvent`/`unpinEvent` carry only the event id, since the daemon labels the pin from that event and refuses ids of anything but a `userMessage`/`assistantMessage` (`sessions.Service.Pin`/`Unpin`, `pinLabel`). The side panel lists them, `sc-conversation.reveal(id)` scrolls to the row (`[data-event]`) and asks for older pages until it is drawn, and `sc-message`'s `pinnable`/`pinned` attributes with its `pin` event are the toggle on the message itself.
- A search match names the row it found: `SessionMatch.eventId` is the event's `id`, or a tool call's `callId` (a `toolCall` event has no `id`). The conversation's rows carry it in `data-event` (`sc-message` from `pinnableMessage`, the tool row and the compaction `<details>` in their handlers), so `sc-conversation.reveal`/`revealMatch` find them by that attribute.
- The palette's conversation results are `match:<sessionId>|<eventId>` (`lib/palette.ts`), a `PaletteTarget` of kind `match`; `sc-app-shell` opens the session through `services/session-reveal`, which keeps the event pending until the page draws its history (a page open already hears its bus). `revealMatch` marks the row 2.4 s instead of a pin's 1.2 s and opens a folded `<details>` row, so a compaction's words show.
- A page's history comes in parts: `openSession { events, since }` answers `sessionHistory { part: 'end' | 'older' | 'since', keptBack }`. A page that reconnects asks `since` its last event and `sc-conversation.resume()` takes only what is new; an older page's events are handled oldest first, and a result already drawn is final (`progress(row, state)`), since tools of one reply may run together. `sessions.Service.OlderEvents` counts `keptBack` from the list's start.
- One hub sends the daemon's messages to the sockets (`daemon/app/hub.go`): each is turned into JSON once, a socket hears a session's events only between `openSession` and `closeSession` (a socket that opened none, the desktop app's watcher, hears every session: `everySession`), `eventForPage` drops `toolFinished.output` (the page draws `display`), and a socket whose outbox passes 32 MiB is ended. `ping`/`pong` is the page's heartbeat (`daemon.wake()` when the tab shows again). `services/session-stream.ts` counts the pages showing a session, so one that leaves does not cut another's stream.
- The conversation draws a streamed reply once per animation frame (`drawStreamed`, flushed before `apply`), `ScMessage.drawText` keeps the blocks whose `blockKey` did not change (`sameBlocks` in `lib/markdown.ts`), and rows before the last 40 are `content-visibility: auto` — on every row it broke "follow the end". A command's output shows while it runs through `toolOutput` (`CommandOptions.Live`, `daemon/tools/liveoutput.go`): a message, not an event, so a page that opens late does not get what was already printed.
- A composer keeps its text per place (`draftPlace`, `lib/drafts.ts`, `services/drafts.ts`): leaving a page and coming back finds it; sending clears it.
- The built app is served with `.br`/`.gz` copies made at build (`compressedCopies` in `web/vite.config.ts`), an etag and cache headers (`daemon/app/webapp.go`). It is an installable app: `web/public/manifest.webmanifest`, `sw.js` (keeps the app's own files; never the API), icons from `scripts/make-icons.py`, `services/install.ts` and the Phone topic's install section.
- A browser lists other swcodes as the desktop app does: `services/computers.ts` is the gateway (`askComputers`/`onComputersAnswer`), answered by the desktop app or by `browser-computers.ts` over `computer-store.ts` (the browser's own list). Another swcode is reached across origins: `daemon/app/cors.go` (`withCORS`) lets the origins of paired devices through (`storedDevice.Origin`, `Redeem(code, name, origin)`), the pairing route alone is open, and `access.ts` gives `daemonUrl`/`daemonOrigin`/`homeToken`. `sc-qr-scanner` needs `BarcodeDetector`, which iOS Safari lacks: the code can be typed.
- `daemon/tailnet` asks Tailscale's command line whether the tailnet can give swcode an HTTPS address and has it serve one (`Read`, `Serve`); `daemon/app/tailnet.go` keeps the answer a minute and `publicURL` is the settings' address, else the tailnet's once served. The e2e rig puts a stand-in `tailscale` first on the daemon's PATH (`<home>/bin`), so the machine's own is never asked.
- swcode listens on `127.0.0.1` unless told otherwise; `config.ListenAsBefore` (marker file `listen-checked`) keeps an install that has paired devices on every interface, once. The data folder is the person's alone (0700, files 0600, `keepPrivate`), the page carries a CSP and `nosniff` (`protect`, `pagePolicy`), and a device forgotten loses its open sockets (`devicesockets.go`).
- A summary is asked at the end of the conversation llm-server already holds, with the tools listed so the prompt cache serves (`continuedSummary` in `daemon/agent/compaction.go`, 3000 tokens kept for it), and from a transcript when that fails (`transcriptSummary`). The fake llm-server picks a script by the first **or the last** user message; the tests' request is `summaryRequest`.
- The leading calls of one reply that only read (`Box.RunsTogether`, `waitingTools`) run at once (`readsAtStart`/`runTogether` in `daemon/agent/loop.go`); anything else keeps its order. Usage carries llama.cpp's `timings` (`cachedTokens`, `promptMs`, `predictedMs`), which `speedLine` (`lib/format.ts`) words in the side panel.
- A command the person must answer runs with `terminal { wait: true }`: in a terminal of the app, the call waiting for its end (`terminals.Service.Run`, `hosts.Shell.Announce/Wipe`, `CommandEnd`, at most 30 minutes). `terminalWaiting { callId, terminalId, title }` draws `sc-terminal-wait`, and the session counts as waiting while the command asks (`runningTurn.asksInTerminal`). `bash` hints at it when a command stopped for want of a person (`personHint`); the password card (askpass) stays for this computer's `bash`.
- A session grant by program name vouches for less than it seems, and both sides hold the same rule with the same cases (`shared/permissions/command-programs.ts`, `daemon/permissions`): a variable set before the program, a program that runs its words (`runners`: sudo, env, xargs, npx…) and words that make one run something else (`runningWords`: `git -c`, `npm exec`) are always asked about.
- The file tools stay out of `.git` (`gitFolderProblem`) and the daemon's own git runs nothing a repository names (`git -c core.fsmonitor=false …`). The web tools reach public addresses only, redirects included (`web.PublicClient`, `Deps.Pages`); a notes file that is a link is not read (`notes.Linked`); a job is its session's (`live.startedJobs`).
- `edit` finds its text by its words when the indentation differs (`replaceByWords` in `daemon/tools/textedit.go`, the replacement re-indented to the file's), says so in `EditResult.Note`, and names the nearest lines when it finds nothing (`nearLines`). A project's check after each edit is `Project.afterEdit` (`{file}` stands for the file), run by `afterEdit()` in `daemon/tools/files.go`; what it says, and that it rewrote the file, go back with the edit's result.
- Notes that outgrow what a session reads lose the oldest notes of their longest sections first (`notes.Fit`, `ProjectNote.leftOut`), and the notes tool then asks the agent to tidy the file (`tidyRequest`).
- MCP servers are the daemon's (`daemon/mcp`): `<data>/mcp.json` (`mcpServers`, a `command` over its standard streams or a `url` over HTTP), reached by a `Manager` at start and on `POST /api/mcp`, listed by `GET /api/mcp` (Settings → MCP servers, `sc-mcp-servers`). The client speaks both eras of the protocol: the `initialize` handshake, and from 2026-07-28 none (the revision rides in each request's `_meta`), falling to the second when `initialize` answers -32601 or -32022. Every server tool is `mcp` to the app (`protocol.ToolNameMcp`) and `mcp_<server>_<tool>` to the model: `tools.ServerTool` gives a `Tool` its `Function` and the server's own schema as `Parameters`, `Box.With` carries them beside the box's own, and `sessions.Deps.ServerTools` is asked at each turn of a coding session's main agent (not a chat's, not a subagent's). A call is `permissions.AccessServer`: asked about unless the mode runs everything, allowed for the session by server (`Grants.Servers`). Tests reach stand-in servers only (`daemon/mcp/mcp_test.go` re-runs the test program as one, `e2e/fake-mcp.ts`); no real server was tried.
- The agent's commands run in a sandbox where the project's host can make one (`daemon/hosts/sandbox.go`): `Sandbox.Wrap` turns a command into a bash script that runs it under bubblewrap, so it works the same on `LocalHost` and a `ShellHost`. `hosts.Sandboxes` asks each host once (again after 10 minutes, after 1 when it had none) whether `bwrap` works and what there is to hide (key folders under `$HOME` and, on WSL, `/mnt/?/Users/*`) and to open (package caches): the per-command script only tests paths with shell builtins, since looking each time cost 200 ms. `sessions.sandboxFor` gives a turn its `tools.Context.Sandbox` (nil when `SWCODE_SANDBOX=off`, the project's `sandboxOff`, or a host without one); `bash`, background jobs and the after-edit check run through `tc.inSandbox`. `bash { unsandboxed: true }` and the `terminal` tool are `permissions.Subject.Outside`: asked about whatever the mode, granted apart (`Grants.Outside`), and `permissionRequested.outside` words the card. The test app and the e2e rig turn the sandbox off (`SWCODE_SANDBOX: off`); the tests about it turn it on and skip where the machine makes none.
- A permission request has a fourth answer, `allowProject`: `permissions.AllowedBy(subject)` says what it adds (a command's programs, in the sandbox or outside it, or an MCP tool's server; nothing for an edit), `projects.Service.Allow` keeps it on `Project.allowed { programs, outside, servers }`, and `sessions.grantsOf` reads the project's rules on top of the session's own at every call, so a rule taken back (`removeProjectAllowed { rule, name }`, the Config tab's `sc-project-allowed`) is asked about again at once. The card's two wider answers come from one `Grant` in `web/src/lib/tool-labels.ts` (`sessionGrantLabel`, `projectGrantLabel`).
- A project added from a folder that was already there starts `untrusted` (`projects.Service.Create`; a folder swcode made, and the one a session was started in, do not): its sessions then get neither its notes (`Setup.Notes` gives none) nor its own skills (`catalog.Place.PersonalOnly`), and `sandboxFor` keeps its sandbox whatever `sandboxOff` says. The app asks once when the dialog made the project (`sc-app-shell.openNewProject`, a `confirmDialog`), the project page shows a banner with the button until it is trusted, and the Config tab's "Trust and sandbox" card (`sc-project-sandbox`) holds both switches; all send `setProjectTrust`. E2E tests that add a folder through the dialog answer the question first.
- `swcode run` (`daemon/headless`, `cli.KindRun`, `local.RunSession`) is a client of the running daemon, which it starts when needed: it sends `createSession` over the socket, follows that session's events until `turnFinished`, declines what nobody can answer, and ends on a `runFinished` line with `--json`. `scripts/eval.ts` (`npm run eval`) drives it over `evals/tasks/<name>/{task.json,files/}` and checks each workspace with the task's `check`; its tests are in `evals/tests` (vitest's `include` names them), and every task's check is tested to fail on its starting files.
- Markdown is parsed in `web/src/lib/markdown.ts` (italics, strikethrough, quotes, nested lists, rules) and code is coloured by a tokenizer of swcode's own (`lib/highlight.ts`, tokens from `--jl-*` only, unknown languages plain); a code block carries its `language`, and its copy button is `sc-message`'s. Everything is still built as nodes, never `innerHTML`.
- The person's own agents are `.agents/agents/<name>.md` in their home and in the project (`catalog.FindAgents`; a project's own are left out for an untrusted folder): frontmatter `name`, `description`, `tools`. The model is told of them with the skills (`skillsListed.agents`), and `agent { agent }` starts one with `tools.AgentBox`. It runs under `sessions.grantsOf` with nobody to ask: a call that would ask ends its task, and its report says why. Its writes are in no restore point (it outlives the turn that started it) and the after-edit check does not run for it.
- `reviewChanges { sessionId }` answers the asking socket with `reviewChanges { branch, files, more?, problem? }` and `commitChanges { sessionId, message }` with `changesCommitted { problem? }` (`sessions.Service.Review`/`Commit` in `daemon/sessions/review.go`, `sc-review`, the session header's `.review` button, hidden for chats). One host script lists `git status -z` against `HEAD` and copies the `HEAD` versions into `<scratch>/review`, read back with `ReadFile` since a command's output is clipped; at most 50 files, binary ones and those over 1 MiB listed without lines. A commit is `git add -A -- . && git commit -m` as the person, outside the sandbox.
- `createSession.worktree` makes `git worktree add -b swcode/<id8> <repo>.swcode-<id8>` beside the repository (`daemon/sessions/worktree.go`); the session works there, and `Meta.WorktreeOf`/`Branch` reach the page as `worktreeOf`/`branch`. Whatever looks a session's project up goes through `Meta.projectFolder()` in the daemon and `projectFolderOf` on the page, so a worktree's session is in its project. Its sandbox opens the repository's `.git` (`Sandbox.Writable`) with its hooks and config read-only (`Sandbox.Kept`), or it could not commit. Deleting the session removes the worktree and keeps the branch.
- A project's schedules live on `Project.schedules` in `projects.json` (`addProjectSchedule`/`setProjectScheduleOn`/`removeProjectSchedule`, the Config tab's `sc-project-schedules`); `projects.Due(schedule, last, now)` is pure, and `App.RunDueSchedules` runs every minute from `watchSchedules`, starting a session with the project's defaults. A slot missed while the daemon was off runs once. The test app's clock is `testapp.Options.Now`.
- **A new enum must not export a list const whose name the Go generator turns into the type's**: `SCHEDULE_EVERY` clashed with `ScheduleEvery`.
- Web Push is `daemon/push`: a VAPID key and at most 20 subscriptions in `<data>/push.json`, RFC 8291 `aes128gcm` and an ES256 JWT (its signature r||s, not ASN.1) with the standard library only; a push service's 404 or 410 drops the subscription. `daemon/app/push.go` feeds the sessions' broadcasts to `desktop/watch.Tracker`, so a push says what the desktop app's notifications say; the routes are `GET`/`POST`/`DELETE /api/push`, and a subscription made with a paired phone's token goes when the phone is forgotten. `sw.js` shows the push and posts `openSession` to an open window (`services/push.ts` `followPushes`); the Phone topic holds the button, worded by `lib/push-view.ts`. A subscription's address must be HTTPS (loopback HTTP is let through for the tests). Never sent to a real push service: the tests decrypt what a stand-in receives.
- **A fixture folder named like something `.gitignore` ignores is not committed** (`data/`, `dist/`…): an eval task lost its files that way, its test passing only where they were made. `git status --short --ignored <folder>` shows them.

## Gotchas met so far

- **`BASE_STYLES` defines `.label`** (the small capitals over a group): a component's own element named `label`
  gets that style. The button's text span is `.text` for that reason.
- **Inputs named like `HTMLElement` properties** (`role`, `title`, `hidden`…) clash with them: the message's
  author is `author`, not `role`.
- **Jadis JSX makes HTML elements only**: SVG is built with `createElementNS` (`lib/mark.ts`, lucide's
  `createElement` for icons).
- **`field-sizing: content` sizes the width too**: a textarea using it needs `width: 100%`, or its placeholder
  makes the page wider than a phone screen.
- **A new Playwright page is a new browser profile**: it has no access token. Open the link with `?token=` first,
  then navigate.
- **A subagent's own events never enter the session's list**: only `subagentStarted`, `subagentActivity` and
  `subagentFinished` do. Recording its `toolCall` or `assistantMessage` events would draw them as the main agent's
  and send them to the main model.
- **Biome's `useSortedKeys` reorders object keys**; the route table keeps its order with a `biome-ignore`.
- **jlib's page outlet keeps the page shown until the next one is ready**: both are in the document a moment, so
  the e2e `settle` waits for one page; Playwright's selectors reach into shadow roots, `jl-page-outlet > *` matches
  its insides too.
- To see the app without a window: `npm run test:e2e` (its global setup builds the Go daemon into `dist/e2e`, and
  `e2e/rig.ts` starts it, the fake llm-server and Chromium for each test). Send a no-op `page.evaluate('0')` after
  each click: headless clicks land on the next command. The e2e code is typed for Node only: run DOM code in the
  page as an expression string.
- **A jl-* component's events do not bubble** (`press`, `change`…): a listener on a list never hears the buttons or
  switches drawn in it. Make each with `createElement(JlButton, …)` and register its own event.
- **jlib's select takes an empty value for nothing chosen**: a real choice that means "the default" gets a value of
  its own on the page (`daemon-folder`, `default`), turned back into the empty setting when saved.
- **Class-form JSX takes no `attrs`** (`<JlField attrs={…}>` does not compile): make the element with
  `createElement(JlField, { attrs, props })` when it needs an attribute.
- **`jl-load-state`'s Try again runs the last `load()` again by itself**: a `retry` listener that loads again
  fetches twice.
- **A Windows process started from WSL ends with the WSL session that started it** (WSL keeps them in a job): the
  daemon's hidden `wsl.exe` is made through WMI (`Win32_Process.Create`) to outlive a shortcut's session. From the
  agent's shell, `Start-Process` on a shortcut or a new console does nothing: to test a double-click, have WMI
  start `explorer.exe "<the .lnk>"`.
- **The daemon stops when its terminal goes away** (a hangup): whatever starts it detached from a terminal
  (`swcode daemon`, which a service's `serve --service` does not use) gives it a session of its own and sends its
  output to a file.
- **The tools never touch the disk themselves**: they go through the context's `Host` (`hosts.LocalHost`, or a
  `hosts.ShellHost` for WSL and SSH), and paths use the host's style (`Paths()`, POSIX or Windows).
- **The web tools run in the daemon, not on the project's host**: the context's `Web` (`daemon/web`). A page's text
  only ever goes to the reader model, which has no tools (`daemon/web/reader.go`): never hand page text to an agent
  that can run commands.
- **A `ShellHost` script never takes a value as it is**: paths go through `ShellWord`, anything else (a command, a
  pattern, bytes) in base64 decoded there. Each script runs in a subshell of the open bash, so its `exit` and `cd`
  stay there.
- **Ubuntu 26.04 has uutils coreutils, bfs and ugrep** in place of GNU's: try a `ShellHost` script on WSL before
  relying on a flag.
- **Windows has no process groups**: a command is stopped with `taskkill /T` (`daemon/hosts/run_windows.go`).
